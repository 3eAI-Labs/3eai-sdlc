# Retrospective — Learning From the Last Stretch of Work

## Purpose

Look back at a stretch of work, find what helped and what got in the way, and agree on a few changes to try next.

## Rules

1. Fix the period first (from a date, a version or a commit to now) and say it.
2. Base it on evidence: the commits, the test results, the issues and the stage documents of the period. Count from the history; mark an impression as one.
3. List what went well, and why, so it can be kept.
4. List what did not go well: delays, rework, failures, surprises. For each, the likely cause, not who is to blame.
5. Agree on a few actions, each with what will change, who does it and how it will be checked. Prefer actions the team can take itself.
6. Check the actions of the last retrospective: done, not done, and whether they helped.
7. Write it down where the project keeps such notes, with the date, so the next retrospective can compare.

## Review checklist

- [ ] The period is stated.
- [ ] Claims rest on the history, or are marked as impressions.
- [ ] What went well and what did not are both listed, with causes.
- [ ] Each action has an owner and a way to check it.
- [ ] The last retrospective's actions were followed up.
